## 测量方法和实验

1. 读取 APK ZIP 中央目录：927 个有效条目，条目压缩后合计 159,817,231 字节。
2. 比较条目的实际字节区间：发现 145,126,000 和 35,288 字节两段未被目录引用的填充区，绝大部分为零。另有 4,096 字节 APK 签名块。空白区的具体产生环节尚未用干净构建作对照确认；不能将全部包格式开销都算成空白。
3. 用 NDK `llvm-readelf` 读取 ELF 段，在副本上用 `llvm-strip --strip-all` 去除调试和普通符号，库降到 16,885,832 字节。
4. 对比 strip 前后带 `SHF_ALLOC` 且占文件空间的 21 个段，SHA-256 均一致，包含运行时所需动态符号等。
5. 重新封装全部有效 ZIP 条目，仅替换为上述库副本，原先不压缩的 DEX、原生库与资源表仍不压缩，实验内容包为 31,696,589 字节（31.70 MB），减少约 89.6%。

实验文件位于 Git 忽略的 `deploy-artifacts/android/size-analysis/`，其中 `payload-analysis-only.zip` 只用于体积测量，未生成 APK 所需签名及原生库对齐，不可作为安装包。未修改当前交付 APK、生产代码或用户数据。尚未测试瘦身后 APK 的安装、启动、后台提醒和拍照流程。

## 后续优化顺序

1. 用干净打包确认并消除大块保留空白，校验最终 ZIP 的有效内容与包大小。
2. 保留本机调试符号文件，手机交付包移除完整调试信息和普通符号。
3. 采用独立的手机发布配置，验证 Rust 优化、Android R8 和资源缩减；检查反射 / JNI / Tauri 插件保留规则，不能直接删除未知依赖。
4. 沿用既有应用标识和可覆盖安装的签名，验证健康记录、照片、通知后台采集、提醒、私人同步及旧数据保留后再替换交付包。

31.70 MB 是当前代码的内容封装实验结果，不是最终发布 APK 大小承诺。正式发布还涉及签名、对齐、代码优化与功能验证。无需先删业务功能即可处理占比最大的两项。

## 与运行内存的区别

以上测量为安装文件所占存储空间。空白填充和不参与运行加载的调试段不会按文件大小等量占用运行内存。实际运行内存还取决于 WebView、页面图片解码、数据库连接、Java / Rust 堆及后台进程，需要在实体手机按空闲、拍照和后台采集等场景单独测量。

参考：[Android 官方 APK 瘦身说明](https://developer.android.com/topic/performance/reduce-apk-size)、[Cargo 编译配置与符号剥离](https://doc.rust-lang.org/cargo/reference/profiles.html)。
