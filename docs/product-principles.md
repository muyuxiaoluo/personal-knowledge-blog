# 浅羽产品原则与事项模型

浅羽是一个本地优先的工作与生活助手。用户可以随手记录、恢复一件搁置的工作，或带着已有资料向浅羽求助。浅羽围绕用户的目标调用合适的工具，减少重复输入和日常维护。AI 日报保留在高频位置，健康、餐食、财富和天气按需打开。

## 事项如何归属

| 概念 | 何时使用 | 与其他事项的关系 |
| --- | --- | --- |
| 想法与资料 | 想保留灵感、线索或参考资料，投入与否仍待决定 | 默认快速保存为笔记，可关联到项目；需要作取舍时再进入提案评估 |
| 行动 | 可以直接着手，结束条件明确 | 可以独立存在，也可以归属一个项目，按需关联一个阶段 |
| 项目 | 有可验收的结果，且值得持续规划、协调与接续 | 从名称与预期结果开始。下一步和里程碑可留空。可以独立，也可以挂在一个上级项目下 |
| 里程碑 | 项目中的重要事件、结果或转折点 | 可以关联行动和日期。日期明确后，里程碑显示在日历中 |
| 持续领域 | 需要长期关注的主题，例如健康 | 可以用可选标签组织相关项目。持续领域无需独立入口、完成率或默认打卡 |

例如，研究生阶段可以是以毕业为终点的项目，期末考试可以是其中的里程碑。复习一章和一次可独立验收的代码委托都可以是行动。独立科研课题可以设置上级项目。主题相近的项目可以共用可选标签。这些例子用于验收，通用界面采用「新建项目」「添加行动」「资料与记录」等中性文案。

## 现有数据如何复用

| 现有记录 | 改造中的用途 |
| --- | --- |
| `Project`、`Milestone` | 沿用项目与里程碑。默认从无路线开始，按需加入线性路线或并行节点。界面按状态和多标签筛选，旧分类字段继续供现有流程读取。父子关系最多一层。 |
| `ProjectTask` | 同时承载独立与项目行动，`projectId = null` 表示独立行动。通过状态、`currentFocus`、`waitingFor` 和 `resumeAction` 表达接续内容、等待对象及恢复后怎么做。等待与暂停分别表达外部条件和投入决定；界面可先呈现行动的等待状态。 |
| 笔记（`Article`） | 作为随手记录和资料入口，以 `projectId` 挂载，原笔记继续作为编辑来源。 |
| `ProjectProposal` | 保留待决定事项、评估内容和决定状态，通过项目资料查看。采纳提案与创建行动是两个明确的操作。 |
| `ProjectAccumulation` | 保留观察、结果和引用。用户可以把有依据的记录标记为已确认成果，也可继续补充同类成果。 |
| `ProjectLog` | 提供行动进展、完成记录、路线调整和项目方向历史。方向调整记录包括旧目标、新目标与时间。 |
| 持续领域 | 先确立使用边界。目前的 `LifeDomain` 是分类值，现有项目与分类按原样读取。独立的领域存储等实际关联需求明确后再设计。 |

项目详情优先回答「上次做到了哪里」「现在能做什么」。优先读已有进度和完成记录，注明来源，区分用户确认的结果、外部资料与 AI 建议。现有大厅的 `nextTask` 可能指向 `waiting`，界面应按行动状态展示等待条件或可执行的下一步。确实没有行动时允许留空。日期区分明确截止和预期目标，日期未定可以留空。

## 实施顺序

1. 确立事项模型与现有记录的映射，以本文作为大厅、详情和后续 AI 改造的依据。
2. 重组项目大厅和详情。大厅支持状态、搜索与项目多标签，详情同时展示目标、里程碑路线和当前状态。「资料与记录」汇集关联笔记、成果、提案、日志和委托。日历可打开有日期的里程碑所属项目，明确截止进入现有待关注。用旧项目、独立行动、没有下一步的项目、并行里程碑和父子项目验证视图与数据完整性。
3. 补齐行动入口。「行动」与项目共用同一条行动记录，首页面显示今天已确认的安排、可继续的行动和待确认的委托。日期与预计工期只提供开始提示，安排由用户确认。计时、补记与调整周计划按需打开。

4. 建立有来源的项目事实和决策上下文，再改进 AI 的建议与计划调整。使用已记录的等待条件、已有决定、已确认成果和 Worker 结果。项目事实不足时，浅羽可以让 DeepSeek 自动核对本次勾选的关联笔记节选。优先接续现有行动，必要时提出一次委托、确认一个条件、等待外部结果或提出局部调整。当前安排适用时保留原安排。

项目咨询、项目内选中的任务线和行动中心的项目起步使用同一套判断规则。任务线读取当前节点、前置节点和项目共享资料。各条记录标明来源和时间，历史目标、用户确认成果与 Worker 报告分别作为判断依据。授权笔记只在决定需要澄清或等待且仍有关键缺口时读取。

新行动需要可核对的完成条件，加入项目时复核重复项及项目状态。委托建议带入现有 Codex 委托表单，由用户检查目录、工作范围和验收条件后确认。报告变化先判断是否有改动的必要，局部草案须逐项勾选，应用前复核项目版本。
5. 在现有本地模型环境中引入结构化能力路由，从记录、查询和调用已有 Worker 等操作开始。语义交给模型判断，应用校验参数和权限。
6. 按真实使用需求扩展可替换 Worker 和可修订的个人记忆。

近期范围限于事项模型和项目体验。现有记录、标识和关联原地复用，数据迁移、新生活模块、持续采集和多模型接入留待相应需求验证。跨模块改动要对应一条真实使用流程，优先检查从打开项目到继续行动所需的步骤、重复输入次数，以及资料和结论能否回溯。
